=head1 NAME

OpenTelemetry::Processor::Batch - A base class for OpenTelemetry batch processors

=head1 SYNOPSIS

    ...

=head1 DESCRIPTION

This is a base class for processors that operate on batches of records. It
is intended to implement the core behaviours that are needed regardless of
whether this is processing trace spans, log records, or metrics.

This processor is intended to be used in production environments where
performance is important. Records handed to it are sent to an I<export
child>: as soon as the first record arrives, the processor spawns a
subprocess that owns the queue of records, the batch boundaries, and the
schedule, and exports them through the exporter on its own. This allows
the main process to continue executing without any delay added by the
export step, and without requiring an event loop to be running: the
subprocess runs a selector loop with the schedule deadline as its
timeout, which is what lets it export a partially filled batch on time
even when the emitting process stops sending records. The exporter itself
is never serialised: the subprocess is a fork of the emitting process and
uses that process's own copy of the exporter.

The specification requires batch processors to synchronise calls to the
exporter, so a processor runs at most one export at any given time: the
single export child deals with the records in the order they were sent.

=head1 FORKED PROCESSES

A processor created in one process cannot reuse the export child of that
process in a process created with L<perlfunc/fork>: the child belongs to
the parent, it holds the records the parent sent it, and its command and
acknowledgement channels are shared with the parent. The processor
notices that it has been inherited on its first use in the forked
process: the inherited channels are closed there (which only releases
this process's copies of those descriptors, the parent holds its own),
and the parent's export child is never waited for nor signalled by the
forked process.

After that, the forked process works as if the processor had been created
in it: the next record received spawns a fresh export child of its own,
so a forked process also exports in the background rather than blocking
on the export. The locks used internally are recreated in the child
transparently, see L<OpenTelemetry::SDK::Lock>.

The export child itself is forked from the middle of whatever the
emitting process was doing, so it closes every descriptor it inherited
except standard input and output and the channels it runs on. Anything
else belonged to the emitting process: an accepted client connection
whose copy the export child kept alive would have stayed open after the
serving process closed its own, leaving a client talking to a live
connection that no process will ever read again. A fork that leaves such
descriptors behind tends to hang clients rather than crash them, which
is why the subprocess sweeps them at the start.

=head1 METHODS

This class implements the L<OpenTelemetry::Processor> role. Please consult
that module's documentation for details on the behaviours it provides.

=head2 new

    $processor = OpenTelemetry::Processor::Batch->new(
        exporter         => $span_exporter,
        batch_size       => $batch_size // OTEL_BSP_MAX_EXPORT_BATCH_SIZE,
        exporter_timeout => $timeout    // OTEL_BSP_EXPORT_TIMEOUT,
        max_queue_size   => $queue_size // OTEL_BSP_MAX_QUEUE_SIZE,
        schedule_delay   => $delay      // OTEL_BSP_SCHEDULE_DELAY,
    );

The constructor takes a mandatory C<exporter> parameter that must be set to an
instance of a class that implements the L<OpenTelemetry::Exporter> role.

It also accepts the following optional parameters:

=over

=item C<batch_size>

The size of the batch of spans to send to the exporter. If not set, this will
read the default value from the
L<"OTEL_BSP_MAX_EXPORT_BATCH_SIZE"|OpenTelemetry::SDK/OTEL_BSP_MAX_EXPORT_BATCH_SIZE>
environment variable, which in turn defaults to 512.

=item C<exporter_timeout>

The number of milliseconds to send to L<OpenTelemetry::Exporter/export>. If
not set, this will read the default value from the
L<"OTEL_BSP_EXPORT_TIMEOUT"|OpenTelemetry::SDK/OTEL_BSP_EXPORT_TIMEOUT>
environment variable, which in turn defaults to 30000.

=item C<max_queue_size>

The maximum size of the internal queue. If not set, this will read the
default value from the
L<"OTEL_BSP_MAX_QUEUE_SIZE"|OpenTelemetry::SDK/OTEL_BSP_MAX_QUEUE_SIZE>
environment variable, which in turn defaults to 2048.

If an attempt is made to queue a record when the queue is full, the older
records will be removed from the queue until there is enough space for the
newer ones. The queue lives in the export child, so this is reported to
L</report_dropped> with the C<buffer-full> reason and the number of
records that were dropped as part of the next acknowledgement: a flush or
shutdown that waits for one sees it, and while no command waits these
counts stay unreported.

=item C<schedule delay>

The delay in milliseconds between scheduled exports of a partially
filled queue. If not set, this will read the default value from the
L<"OTEL_BSP_SCHEDULE_DELAY"|OpenTelemetry::SDK/OTEL_BSP_SCHEDULE_DELAY>
environment variable, which in turn defaults to 5000. A negative value
logs a warning and uses the default.

The countdown starts when a record reaches an empty queue, and a new
countdown starts at every export for the records it leaves behind. The
countdown is kept by the export child, which exports the partially filled
queue the moment it runs out, even when the emitting process stops
sending records: no event loop in the emitting process is needed, and no
L</force_flush> call is required to get idle records out.

A partial queue is only exported on its own while the export child
exists: the first record spawns it, and it leaves when the processor is
shut down.

=back

=head2 process

    $processor->process( @records );

Takes a list of records that are ready for processing. Once called, this
method hands them to the export child, which queues them there: a batch
of L</batch_size> records goes out right away, and a partially filled
queue goes out when the L</schedule delay> countdown runs out, in either
case without this call waiting for the export.

Records given to a processor that has been shut down are ignored: they
are neither queued nor exported.

The records are handed over without waiting for their export: the result
of that export cannot be known at the time of the handover, so it is not
reported through L</report_result>. Only the records this process waits
for (during L</force_flush>) report their results. Records that cannot be
handed over to the export child are not exported in this process either:
that would block the caller for as long as a failing exporter takes to
time out. They are reported to L</report_dropped> with the
C<subprocess-failed> reason instead, and the next call spawns a fresh
export child.

Since this processor works only when a batch is ready, it can sometimes make
for more complicated debugging. For a simpler processor that handles each
record as it becomes ready and blocks during the export step, see
L<OpenTelemetry::Processor::Simple>.

=head2 report_dropped

    $processor = $processor->report_dropped( $reason, $count );

Reports the number of dropped records for the specified reason. The reason
must be usable as a string, and the count must be usable as a number.

The method in this class does nothing, but subclasses can extend it.

This method returns the calling instance, and is suitable for chaining.

=head2 report_result

    $result = $processor->report_result( $result, $count );

Takes an L<export result|OpenTelemetry::Constants/Export Results> and the
number of records that that result applies to, and reports this result.

It returns the export result, so it is suitable to be used when returning
from an exporting function.

The method in this class does nothing. It is expected to be extended by
subclasses.

=head2 force_flush

    $result = await $processor->force_flush( $timeout );

Empties the queue held by the export child by sending any unexported
records to the exporter.

This operation is synchronous for the caller: it blocks until every
queued batch has been exported and the export child (if one is running)
has acknowledged the flush order. Takes an optional timeout in seconds.
When the time runs out, this call returns a timeout result but does not
stop the export child: it was told to drain to the end, so the records it
did not finish with stay in its queue and go out with its next scheduled
export. Late answers to an abandoned flush are recognised and discarded.

When an export fails, the flush keeps exporting the rest of the queue and
returns the first failed result.

This method will also call L"force_flush"|OpenTelemetry::Exporter/force_flush>
on the configured exporter. It returns a L<Future> that will hold the result
of that operation.

=head2 shutdown

    $result = await $processor->shutdown( $timeout );

The specification wants shutdown to include the effects of a
L</force_flush>, so the order sent to the export child makes it export
everything still in its queue, call
L"force_flush"|OpenTelemetry::Exporter/force_flush> and then
L"shutdown"|OpenTelemetry::Exporter/shutdown> on the configured exporter,
and acknowledge with the result: the shutdown's own result if it failed,
and otherwise the first failure of the drain or the flush it implies.
This call waits for that acknowledgement within its optional timeout;
when the wait runs out the export child is killed, and the records it
still held are lost.

Once the processor has been shutdown, any additional calls to
L</process>, L</shutdown>, or L</force_flush> do nothing: the records are
not queued or exported, and the calls immediately return a success
result.

=head1 METRICS

Metrics are reported using L<Metrics::Any>. Please consult the documentation
of that module to learn how to redirect where they are sent to. The
signal-specific subclasses (such as
L<OpenTelemetry::SDK::Trace::Span::Processor::Batch>) turn the reports
below into counters. At the time of writing, these metrics are
non-standard, but their inclusion in the standard
L<is being discussed|https://github.com/open-telemetry/semantic-conventions/issues/83>.

The queue and the exports of this processor live in the export child,
where a metrics registry of this process would not be able to see them.
What the child learns (records dropped from a full buffer, and the
results of drains waited for by L</force_flush>) reaches this process
through acknowledgements and is reported from here through
L</report_dropped> and L</report_result>, which subclasses turn into
metrics.
